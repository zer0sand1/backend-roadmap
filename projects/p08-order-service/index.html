Project Overview

Build an order management system with products, inventory, carts, and orders. The core challenge: handle concurrent purchases correctly. Implement optimistic and pessimistic locking. Use database transactions for atomicity. Add idempotency keys to prevent double charges. This project teaches you the hardest part of backend engineering - getting concurrent data modifications right.

POST /orders {items, idempotency_key}
         |
    FastAPI + SQLAlchemy
         |
    BEGIN TRANSACTION
         |
    1. Lock inventory rows (SELECT ... FOR UPDATE)
    2. Check stock levels
    3. Deduct quantities
    4. Create order + order_items
    5. Process payment (mock)
    6. COMMIT
         |
    If any step fails -> ROLLBACK (or compensating transaction)
📄

Project Specification

  • Products with name, price, stock_quantity, version (for optimistic locking)
  • Cart: add/remove items, view cart
  • POST /orders creates order from cart (atomically)
  • Idempotency key header prevents duplicate orders
  • Two locking strategies: optimistic (version column) and pessimistic (SELECT FOR UPDATE)
  • GET /orders/{id} returns order status
  • GET /orders/{id}/status for polling
  • Checkout flow: validate stock -> reserve inventory -> create order -> process payment -> confirm
  • Failed payment triggers order cancellation + inventory restock (compensating transaction)
  • Admin endpoint to view all orders with filtering
📖

What to Read Before Starting

  • ACID properties: Atomicity, Consistency, Isolation, Durability (read "Designing Data-Intensive Applications" Ch 5)
  • Transaction isolation levels: READ COMMITTED, REPEATABLE READ, SERIALIZABLE
  • Pessimistic locking (SELECT ... FOR UPDATE) vs optimistic locking (version column)
  • Idempotency keys: why payment processing requires them (read Stripe docs on idempotency)
  • Saga pattern: choreography vs orchestration for distributed transactions
  • Deadlock detection and prevention strategies
🚀

What You'll Learn

  • SQLAlchemy session management and transaction boundaries
  • SELECT ... FOR UPDATE for pessimistic row-level locking
  • Optimistic locking with version column and retry logic
  • Idempotency key creation, validation, and deduplication
  • Compensating transactions for partial failure recovery
  • Concurrent test writing (verify 2 users buying last item)
🔧

Implementation Steps

  1. Define models: Product (with version column), Cart, CartItem, Order, OrderItem
  2. Seed products with initial stock
  3. Build product listing and detail endpoints
  4. Implement cart add/remove with stock validation
  5. Implement POST /orders with idempotency key check
  6. Add pessimistic locking (SELECT ... FOR UPDATE within transaction)
  7. Add optimistic locking as alternative (catch StaleDataError, retry)
  8. Mock payment processing step with failure simulation
  9. Add compensating transaction for payment failure (restock inventory)
  10. Write concurrent test (using asyncio.gather or threading)
✓

Verification Goals

  • Two concurrent requests buying the last item - one succeeds (200), one gets 409 Conflict
  • Same idempotency key returns same result without creating duplicate order
  • Inventory count is always accurate after concurrent purchases (verify in DB)
  • Order creation is atomic: if payment fails, inventory goes back to original state
  • Optimistic lock raises StaleDataError; retry succeeds on next attempt
  • Deadlock doesn't occur under moderate concurrency (test with 10 concurrent buys)
  • Order status transitions correctly: pending -> confirmed -> shipped
