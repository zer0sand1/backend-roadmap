Project Overview

Build a real-time multi-room chat application. Users connect via WebSocket, join rooms, send messages. Use Redis Pub/Sub to broadcast across multiple server instances. Manage connection lifecycle (connect, disconnect, reconnect). Build a minimal HTML/JS client to test it. This project teaches you bidirectional communication - the foundation for notifications, live updates, and collaborative features.

Project Specification

  • WebSocket endpoint at ws://localhost:8000/ws/{room_id}?token={jwt}
  • Users join a room on connect, leave on disconnect
  • Messages broadcast to all users in the same room
  • System messages (user joined, user left) for each room
  • Message format: {"type": "message|join|leave", "user": "...", "text": "...", "timestamp": "..."}
  • Multiple rooms isolated from each other
  • Redis Pub/Sub keeps rooms in sync across server instances
  • Heartbeat/ping-pong every 30 seconds to detect dead connections
  • Message history (last 50 messages per room in Redis)
📖

What to Read Before Starting

  • WebSocket protocol: upgrade handshake, frames, opcodes (read RFC 6455)
  • WebSocket vs SSE vs long polling: trade-offs
  • Pub/sub pattern: publishers, subscribers, channels, message brokering
  • Connection lifecycle: OPEN, CLOSING, CLOSED; on_connect, on_disconnect
  • Scaling WebSockets: why sticky sessions aren't enough, need external pub/sub
  • FastAPI WebSocket: accept, receive_text, send_text, close, disconnect handling
🚀

What You'll Learn

  • WebSocket endpoint in FastAPI with authentication
  • Managing connected clients (dict of room -> set of WebSocket connections)
  • Redis Pub/Sub to broadcast across multiple server instances
  • Heartbeat/ping-pong to detect and clean up dead connections
  • Graceful shutdown: drain connections on server stop
  • Building a minimal browser-based chat client with vanilla JS
🔧

Implementation Steps

  1. Add WebSocket endpoint in FastAPI with JWT auth on connect
  2. Build ConnectionManager class that tracks room -> connections mapping
  3. Handle connect (add to room, broadcast join message)
  4. Handle disconnect (remove from room, broadcast leave message)
  5. Handle incoming messages (broadcast to all room members)
  6. Add Redis Pub/Sub for cross-instance message broadcasting
  7. Add heartbeat check (ping client, remove if no pong in 60s)
  8. Store last 50 messages per room in Redis list
  9. Build HTML/JS client with room list and message input
  10. Test with 2 browser tabs + 2 server instances
✓

Verification Goals

  • Two browser tabs in the same room show messages in real-time (<500ms delay)
  • Messages in Room A don't appear in Room B
  • Disconnecting a client shows "user left" message to other clients
  • Running 2 server instances, messages sync across both (via Redis)
  • Server handles 50+ concurrent WebSocket connections without slowdown
  • Reconnecting client receives last 50 messages from history
  • Closing browser tab cleans up within 60 seconds (heartbeat detect)
